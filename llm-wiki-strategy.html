1 · 한 줄 요약

LLM-wiki는 개인·팀의 연구 기억층(research memory)으로 즉시 가치를 주며, AI Co-Scientist의 핵심 메모리 구조로도 매우 적합하다. 단, 온톨로지 백본·외부 검증 도구·엄격한 lint 라는 조건부다.

본질은 단순하다 — Co-scientist의 "가설 ↔ 증거 ↔ 비판 ↔ 갱신" 루프와 LLM-wiki의 "ingest ↔ query ↔ lint" 루프가 구조적으로 같다. 문제는 환각 누적과 결정적 검증의 부재이며, 두 가지 모두 설계로 통제 가능하다.

2 · 왜 중요한가

연구·R&D의 자산은 "축적되는 지식"인데, 기존 도구는 그 자리를 비워두고 있다

RAG는 매 질의마다 원본을 다시 검색하는 stateless 구조이고, Confluence/Notion은 사람의 정리 노력에 비례해서만 가치가 쌓인다. 그 사이의 빈 자리 — 에이전트가 자료를 읽고 정리·연결을 누적하는 레이어 — 가 LLM-wiki다.

  • 개인 연구: "지난주에 읽었던 논문" 재발견 시간을 0으로 줄이고, 미해결 질문(Open Question)을 잃어버리지 않게 한다.
  • 팀 프로젝트: 결정의 근거가 위키에 박혀 있어, 신규 멤버 온보딩과 재논쟁 비용이 줄어든다.
  • AI Co-Scientist: 가설 카탈로그·비판·반증 이력을 위키에 누적시켜 매 사이클이 이전 사이클 위에서 자라게 만든다.
핵심 통찰: Co-scientist의 generation / reflection / ranking / evolution / meta-review 에이전트 역할은 LLM-wiki의 ingest·query·lint 연산과 구조적으로 동형이다. 별도 메모리 시스템을 새로 설계할 필요가 없다.

3 · 시스템 구조 — 3가지 적용 형태

같은 raw / wiki / schema 골격에, 적용 대상에 따라 페이지 타입과 거버넌스만 달라진다

A. 개인 연구
페이지 타입(5): Concept / Paper / Method / OpenQuestion / Decision.
운영: 주 1회 자동 lint, 매주 OpenQuestion 상태 변화로 진척 측정.
  • 원자 개념 + 합성 페이지의 이층 구조
  • 충돌은 Disagreement 페이지로 명시화
  • git으로 환각 롤백 가능하게
B. 팀 프로젝트
페이지 타입: ADR / Meeting Notes / Stakeholder / Risk / OpenQuestion / Glossary.
운영: 누구나 ingest, 오너만 머지, lint는 CI에서.
  • SSOT 정책 사전 결정 (위키 vs 기존 도구)
  • CLAUDE.md는 PR 리뷰로만 변경
  • mesh sync = git 브랜치 + PR 모델
C. AI Co-Scientist
페이지 타입(5): Hypothesis / Evidence / Experiment / Critique / OpenQuestion.
운영: 생성·비판·랭킹·진화·메타리뷰 에이전트가 각각 다른 브랜치에 쓰고 머지.
  • 도메인 온톨로지(MeSH/GO 등) ID로 개체 정합성 확보
  • 모든 Hypothesis는 status·evidence·confidence 필수
  • lint = 자동화된 동료 검토 (반증 가능성 추적)
설계 원칙: 페이지 타입은 5–6개를 넘기지 않는다. 타입이 늘면 위키가 굳고, 줄면 슬롭이 쌓인다. CLAUDE.md가 곧 거버넌스다.

4 · 기대 효과

적용기대 효과측정 지표(예)
개인 연구 같은 자료 재발견 시간 ↓, OpenQuestion 추적, 인사이트 누적 주당 절감 시간, OpenQuestion 폐쇄율, lint 경고 추이
팀 프로젝트 결정 근거 가시화, 신규 멤버 온보딩 단축, 재논쟁 감소 온보딩 First-Productive-Day, ADR 작성률, 미증거 클레임 0 유지
AI Co-Scientist 가설 누적·반증 이력화, 사이클 간 자기복리, 재현성 추적 가설당 evidence 수, refuted/abandoned 비율, 반복 사이클당 신규 OpenQuestion 수
현실적 기대치: 개인·팀에서는 1–2주 안에 시간 절감이 보이지만, Co-scientist의 "사이클 간 자기복리" 효과는 최소 4–6주 이상 운용해야 가시화된다. 초기에 과장된 ROI를 약속하지 않는 것이 중요하다.

5 · 리스크와 대응

리스크등급발생 맥락대응
환각이 위키에 박혀 누적 (Co-scientist에서 가장 위험) High 모든 적용 페이지마다 출처·신뢰도 라벨 의무, lint를 반증 가능성 추적기로 강화
위키 정리 자체가 목적화 (slop bloom) Med 개인·팀 페이지 타입 5–6개 상한, 주 1회 lint로 고아·중복 정리
SSOT 충돌 (위키 vs Confluence vs Slack) Med 팀 도입 첫 주에 권위 도구 합의, 나머지는 미러로만 사용
도메인 온톨로지 부재로 개체 정합성 깨짐 High Co-scientist 공개 온톨로지(MeSH/GO/SNOMED 등) 또는 경량 자체 ID 사전 마련 후 진입
수치·통계·증명 등 결정적 검증 영역 High Co-scientist 위키 안에서 결론 내지 말 것. 외부 도구(R/statsmodels/Lean) 결과를 ingest
규제·윤리 데이터(임상·개인정보) 혼입 High 팀·Co-scientist 민감 데이터는 별도 보관소, 위키에는 메타데이터·ID만
멀티 에이전트/유저 충돌 Med 팀·Co-scientist git 브랜치 + PR 모델, 충돌 정책을 CLAUDE.md에 명시
레드라인: Co-scientist에서 lint가 healthcheck 수준에 머무르면 가설 위에 가설이 쌓여 몇 사이클 만에 신뢰성을 잃는다. 도입 전에 "lint = 자동 동료 검토"로 설계되어 있는지 반드시 확인한다.

6 · 다음 액션 (제안)

  • Week 1 개인 PoC: 본인 1명 + Claude Code (또는 Codex) 한 도구로 raw/ + wiki/ + CLAUDE.md 5타입 페이지 운영, 주말에 lint 실행 후 결과 검토
  • Week 2 팀 1곳 파일럿 선정: 한 프로젝트에 ADR/OpenQuestion 페이지부터 도입, SSOT 정책 합의, lint를 CI에 연결
  • Week 2–4 Co-scientist 좁은 PoC: 도메인 1개, 가설 5–10개, 사람 1명 + 에이전트 1개로 시작. 평가 질문은 단 두 가지 — (a) lint가 stale·미증거를 잡아내는가, (b) 사이클 간에 가설 품질이 실제로 개선되는가
  • Week 4 의사결정 게이트: 위 두 질문 모두 yes면 도메인 온톨로지 결합 단계로 확장, 아니면 lint·스키마 재설계 후 재시도
  • 분기 거버넌스 정착: 권한 모델, 감사 로그, 환각·stale 비율 KPI를 정기 보고 항목으로 편입
의사결정 요청: (1) 개인 PoC를 진행할 1주의 시간 확보, (2) Co-scientist PoC의 도메인·평가자 지정, (3) 민감 데이터 처리 정책 — 보안·법무 사전 의견.
본 문서는 직전 보고(LLM-wiki 개념 정리)의 후속으로, 활용 전략과 AI Co-Scientist 적용 가능성에 초점을 맞춰 정리한 것이다. 수치는 권장 기간 등 운영 기준이며, 실제 일정과 KPI는 도메인·조직 상황에 맞춰 보정이 필요하다. 외부 CDN 없이 단일 HTML로 작성된 self-contained 보고서다.
