LLM-wiki — 무엇이고, 온톨로지와 어떻게 다른가

문서 유형: 개념 정리 + 도입 가이드
작성일: 2026-05-09

1 · 한 줄 요약

LLM-wiki는 LLM/에이전트가 자료를 읽어 스스로 작성·연결·유지하는 마크다운 위키다. RAG의 대체재가 아니라, 그 위에 시간이 갈수록 누적되는 지식 레이어로 보는 것이 정확하다.

2026년 4월 Andrej Karpathy가 공개한 패턴이 발화점이 됐고, 이전부터 있던 llms.txt(외부 노출용)와 사내 LLM-readable 위키(내부 재구조화)까지 같은 우산 아래 모이고 있다.

2 · 왜 지금 부상했는가

"검색해 답하는 RAG"의 stateless 한계와 에이전트 코딩의 보편화

지금까지 LLM에 외부 지식을 붙이는 표준은 RAG였다. 그러나 RAG는 매 질의마다 원문을 새로 검색·임베딩에 의존하므로 같은 사실을 매번 다시 발견하는 stateless 구조다. 반면 LLM-wiki는 한 번 읽은 자료를 위키 페이지·링크 형태로 컴파일해 두고, 다음 질의에 그 결과를 직접 사용한다 — 시간이 갈수록 정리·연결이 누적된다.

  • 대용량 컨텍스트 윈도우의 보편화로 위키 전체를 통째로 참조하는 워크플로가 가능해졌다.
  • 에이전트 코딩 도구(Claude Code, Codex, Gemini CLI 등)가 파일시스템을 직접 다루며 위키를 자동 갱신할 수 있게 됐다.
  • llms.txt(2024.9 Jeremy Howard 제안)는 외부 사이트가 LLM에 노출하는 요약 표준으로, 같은 흐름의 외향 버전이다.
핵심 구분: "RAG vs LLM-wiki"의 양자택일이 아니라, RAG = 검색 · LLM-wiki = 정리·기억으로 역할이 다르다고 보는 것이 실무에 맞는다.

세 갈래 비교

유형대상·작성자
Karpathy LLM-wiki개인/팀 노트 → 에이전트가 자동 작성
llms.txt웹사이트 → 사람이 작성, LLM이 읽음
사내 LLM-readable 위키사내 문서 → 사람·에이전트 협업으로 재구조화
세 가지는 독립되어 있지만 결합 가능하다. 회사가 사내 위키를 정비하면서 외부에는 llms.txt를 노출하고, 팀 단위로 Karpathy 패턴을 시도하는 식.

3 · 시스템 구조

3-Layer + 3-Ops — 가장 단순하지만 가장 자주 인용되는 형태

Layer 1 · raw/
논문·회의록·웹페이지·코드 등 불변 원본. 절대 수정·삭제하지 않고 그대로 보관해 추적성과 재컴파일을 보장.
Layer 2 · wiki/
LLM이 작성하는 마크다운 페이지 + 상호 링크. 페이지마다 출처(raw/) 링크와 신뢰도 라벨을 붙여 환각·풍문을 분리.
Layer 3 · schema (CLAUDE.md 등)
위키의 규칙·서식·금지사항을 적은 단일 파일. 일관성을 결정하는 가장 중요한 파일이며 사실상 거버넌스다.
▶ ingest로 raw → wiki 컴파일    ◆ schema가 모든 작업의 기준    ◀ lint가 위키를 자가-치유
ingest
새 자료를 읽어 wiki/ 페이지를 새로 쓰거나 기존 페이지에 병합. 링크·출처를 함께 갱신.
query
사용자/에이전트가 위키에 직접 질의. 원본 검색이 아닌 정리된 페이지를 우선 참조.
lint
고아 페이지·stale 클레임·깨진 링크·중복 정의를 자동 감지·수정. 위키가 시간이 갈수록 더 깨끗해지게 만드는 핵심 연산.
확장 패턴: 단일 사용자·단일 에이전트가 기본 가정이지만, 실제 회사에서는 mesh sync — 여러 에이전트가 각자 관찰을 기록하고 충돌을 병합 — 가 필요하다. 이 부분은 아직 표준화되지 않았다.

4 · 온톨로지와 어떻게 다른가

대체가 아니라 상보 — 표현 방식과 추론 방식이 근본적으로 다르다

비교 축LLM-wiki온톨로지 (OWL/RDF, 지식그래프 백본)
표현 형식 자연어 마크다운 + 링크 (사람이 읽을 수 있는 문서) 형식 논리 — 클래스·프로퍼티·제약 (기계가 추론할 수 있는 그래프)
작성 주체 LLM/에이전트가 자동 작성, 사람은 검토·정정 도메인 전문가·온톨로지스트가 설계, 변경에 합의 필요
추론 방식 LLM 추론 — 문맥·확률 기반, 유연하지만 비결정적 규칙·삼단논법 — 결정적·재현 가능, 제약 위반 검출 가능
일관성·검증 느슨, lint로 사후 보정 엄격, 스키마 위반은 적재 단계에서 차단
도입 비용·기간 낮음, 1주 안에 PoC 가능 높음, 모델링·합의·툴체인에 수개월
변화 적응 새 자료를 던지면 즉시 반영 스키마 변경 비용이 크고 거버넌스 절차 필요
강점 비정형 텍스트 캡처, 빠른 시작, 사람-친화 인터페이스 결정적 질의, 컴플라이언스·감사, 정확한 엔티티 식별
약점 환각·출처 추적 약함, 결정적 질의 부적합 비용·경직성, 비정형 데이터·롱테일 표현 어려움
실무 권장 포지셔닝: 온톨로지는 백본(엔티티·관계·제약의 진실 원천), LLM-wiki는 그 위의 자연어 인터페이스·캡처 레이어. 둘이 결합된 형태(예: 위키 페이지가 핵심 엔티티에 ID로 연결)는 엔터프라이즈에서 가장 강력하다는 평가가 다수다.

5-A · 활용 시나리오

대상적합도대표 활용
개인 학습/연구 High 논문·웹·노트를 위키로 자동 정리, 시간이 갈수록 연결도가 깊어짐
팀 프로젝트 High 회의록 → 결정·이슈 페이지 자동 생성, 코드 리포지토리 컨텍스트 위키화
사내 도메인 지식 Med 온톨로지 백본 + LLM-wiki 결합. 권한·감사·출처 라벨링 필수
외부 노출 (제품·문서 사이트) Med /llms.txt 추가로 LLM 친화 요약 노출, 단 채택률·효과는 아직 검증 단계
규제·결정적 질의 영역 Low LLM-wiki 단독은 부적합 — 온톨로지/지식그래프가 주, 위키는 보조

5-B · 도입 단계 (제안)

  • 0–1주 개인 PoC: raw/ · wiki/ · CLAUDE.md 폴더만 만들고 Claude Code 등으로 ingest·query·lint 흐름 체험
  • 2–4주 팀 파일럿: 1개 프로젝트 위키, 출처·신뢰도 라벨 규칙, lint 자동 실행 스케줄 정의
  • 1–3개월 도메인 결합: 핵심 엔티티 20–50개를 가벼운 온톨로지/스키마로 정의하고 위키 페이지가 그 ID에 연결되도록 규칙화
  • 분기 거버넌스 정착: 권한(읽기/쓰기/실행) 모델, 감사 로그, mesh sync 시 충돌 해결 정책
  • 선택 외부 사이트에 /llms.txt 게시 — 효과 측정 후 유지/철회 결정

결정적 질의·규제 영역 부적합 High 해당 영역은 온톨로지/지식그래프를 주 사용, 위키는 인터페이스로만 사용

6-B · 다음 액션

  • 이번 주 팀 1곳을 정해 1주짜리 개인 PoC를 시작 — Karpathy gist 또는 llm-wiki-agent 같은 공개 템플릿 활용
  • 2주차 PoC 결과를 보고 — 해결한 문제 / 환각 사례 / lint가 잡은 오류 3가지로 평가
  • 1개월 사내 도입 시 거버넌스 초안 작성: 출처 라벨 규칙, 권한 모델, 감사 로그
  • 분기 도메인 온톨로지 유무 점검 — 없다면 핵심 엔티티만이라도 가볍게 정의해 LLM-wiki와 연결
의사결정 요청: (1) PoC 담당 팀 1곳 지정, (2) 사내 도입 시 보안·법무 합동 검토 트리거, (3) 외부 노출(llms.txt) 여부는 마케팅·DX 팀 협의로 분리.
참고: Andrej Karpathy의 LLM-wiki Gist(2026.4), llms.txt 제안(Jeremy Howard, 2024.9), Stardog·Atlan·Enterprise Knowledge의 LLM × 온톨로지 결합 논의, NVIDIA의 LLM-driven KG 평가 자료 등을 종합. 인용 수치(예: ~10% llms.txt 채택률, RAG 대비 효율 인용치)는 출처 인용이며 환경에 따라 달라질 수 있다. 본 문서는 외부 CDN 없이 단일 HTML로 작성된 self-contained 보고서다.
